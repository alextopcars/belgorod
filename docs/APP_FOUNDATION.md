# alex.topcars — мобильное приложение и backend

## Статус
Этап 1 — архитектурная основа. Это проектная спецификация, не готовое приложение и не подключённые интеграции.

## Цели продукта
- Единое приложение для Android и iOS на React Native + Expo.
- Отдельная адаптивная веб-панель администратора на Next.js.
- Общий backend на Supabase (PostgreSQL, Auth, Storage, Edge Functions).
- Гостевой режим и регистрация/вход по телефону с одноразовым кодом.
- Каталог автомобилей, избранное, заявки, заказы, CRM-статусы.
- Оформление заявки через Telegram и онлайн-оплата через подключаемого платёжного провайдера.
- Импорт объявлений только через разрешённые API/партнёрские интеграции площадок; без несанкционированного парсинга.

## Стек
| Слой | Технология | Назначение |
|---|---|---|
| Mobile | React Native + Expo + TypeScript | Android/iOS из общей кодовой базы |
| Admin | Next.js + TypeScript | Закрытая панель управления |
| Backend | Supabase | PostgreSQL, Auth, Storage, Edge Functions |
| API | Supabase client + server-side functions | Доступ к данным и бизнес-операции |

## Роли и авторизация
- guest: просмотр публичного каталога; локальное избранное; для отправки заявки можно предложить вход или запросить контакт.
- customer: собственный профиль, избранное, собственные заявки и заказы.
- manager: просмотр и обработка назначенных заявок; изменение статусов в рамках полномочий.
- admin: полный доступ к каталогу, интеграциям, пользователям, ролям и настройкам.

Вход по телефону/SMS реализуется через Supabase Auth и выбранного SMS-провайдера. Гостевой доступ не должен давать права на чтение персональных данных или закрытых заявок. Роли и политики доступа проверяются на сервере и в RLS.

## Основные сущности данных
- profiles: профиль пользователя и роль.
- vehicles: карточка автомобиля, характеристики, цена, валюта, статус, источник.
- vehicle_media: фотографии и порядок отображения.
- favorites: избранное пользователя.
- leads: обращения с типом (vehicle, selection, credit, commission, delivery).
- orders: заказ, сумма, статус, выбранный способ оформления.
- payments: платёжная попытка, провайдер, внешний ID, сумма, статус, даты.
- integrations: подключённые источники и настройки синхронизации (секреты только в серверных secrets).
- import_jobs: журнал синхронизаций, ошибок и количества импортированных записей.
- audit_log: журнал важных действий администраторов и менеджеров.

## Интеграции автомобильных площадок
Каждая площадка подключается отдельным адаптером:
1. Проверить наличие официального API, партнёрской программы и право повторной публикации контента.
2. Хранить ключи только в серверных секретах, не в мобильном приложении и не в публичном репозитории.
3. Сопоставлять записи по внешнему ID и источнику, поддерживать повторный безопасный импорт.
4. Сохранять дату последней синхронизации, ошибки и состояние объявления.
5. Перед публикацией в приложении проверять актуальность цены и доступность автомобиля.
6. Не использовать scraping/обход ограничений площадок без разрешения.

## Telegram и онлайн-оплата
- Telegram: формировать заявку на сервере, сохранять её в CRM и выдавать пользователю ссылку/кнопку перехода в чат или бот. Не полагаться только на копирование текста в буфер обмена.
- Онлайн-оплата: провайдер выбирается после проверки страны регистрации бизнеса, юридического лица/ИП, валюты, комиссий и требований эквайринга.
- Платёж создаётся серверной функцией. Клиентское приложение не может самостоятельно помечать заказ оплаченным.
- Статус оплаты меняется только после проверки подписанного webhook провайдера; повторные webhook должны обрабатываться идемпотентно.
- Не хранить данные банковских карт. Использовать платёжную страницу/SDK провайдера.
- Для автомобилей с высокой стоимостью предусмотреть отдельное подтверждение условий, суммы, договора и возврата предоплаты до запуска платежа.

## Безопасность и приватность
- Репозиторий с исходниками должен быть private. В текущем репозитории belgорod исходники сайта публичные; эта спецификация размещена в отдельной ветке только как временная точка старта.
- Никогда не коммитить .env, API keys, service_role key, SMS credentials, payment secrets или Telegram bot token.
- Включить RLS на всех таблицах с пользовательскими или бизнес-данными.
- Service role key использовать только на сервере.
- Админ-панель закрыть авторизацией, MFA по возможности, проверкой роли и журналом действий.
- Для заявок и платежей предусмотреть rate limiting, валидацию, защиту от повторной отправки и резервное копирование.

## Этапы реализации
### Этап 1 — основа
- Утвердить архитектуру, репозиторий, окружения и правила безопасности.
- Создать схему БД и RLS.
- Настроить Expo/Next.js монорепозиторий и CI.
### Этап 2 — каталог
- Каталог, фильтры, карточки, фотографии, избранное.
- Админ CRUD для автомобилей и медиа.
### Этап 3 — заявки и CRM
- Гостевые обращения, SMS-вход, профиль.
- Лиды, назначения менеджерам, Telegram уведомления.
### Этап 4 — импорт площадок
- Адаптеры официальных API после получения доступов и согласования прав.
### Этап 5 — заказы и оплата
- Платёжный провайдер, server-side checkout, webhooks, тестовые платежи.
### Этап 6 — релиз
- Тестирование устройств, TestFlight, Google Play internal testing, публикация.

## Что нужно решить перед реальной интеграцией
1. Какое ИП/юрлицо будет принимать платежи и в какой стране открыт расчётный счёт.
2. Какие площадки подключать первыми и есть ли партнёрские API-доступы.
3. SMS-провайдер и бюджет на сообщения.
4. Нужны ли онлайн-платежи для полной стоимости или только для согласованной предоплаты/брони.
